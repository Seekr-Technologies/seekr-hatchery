# S3 credential proxy

The S3 sidecar gives a sandbox S3 access without mounting `~/.aws`. Configure
it at the top level of `.hatchery/docker.yaml`:

```yaml
s3:
  default: development
  profiles:
    development:
      # region: us-west-2  # optional; otherwise read from the host profile
      rules:
        - path: s3://project-artifacts/team-a/
          permissions: [READ, LIST, WRITE]
    production-readonly:
      rules:
        - path: s3://production-artifacts/published/
          permissions: [READ, LIST]
```

Each key under `profiles` is both the host AWS profile name and the name visible
inside the sandbox. Profile names may contain letters, digits, dots,
underscores, and hyphens. When exactly one profile is configured, omit
`default` and Hatchery selects it automatically. Multiple profiles require a
`default`.

The configuration model validates input shape and profile-name syntax. Before
building the sandbox image, the S3 sidecar separately verifies that every
configured profile exists in the host AWS configuration. A missing profile
reports the profiles available on that machine.

`region` is optional and defaults to the host profile region or `us-east-1`.

## Credential isolation

Hatchery writes read-only sandbox AWS configuration and credentials files
containing random per-launch credentials. Profiles work with normal client
selection, for example:

```bash
aws s3 ls
aws --profile production-readonly s3 ls
```

One authenticated host-side proxy maps each synthetic access key to its host
profile, refreshes temporary credentials when needed, and signs requests to the
profile's regional AWS S3 endpoint. Real AWS configuration and credentials
never enter the sandbox.

The same configuration applies to task sessions and `hatchery sandbox shell`.

## Path policies

`rules` is an optional additive allowlist. Omitting it preserves all S3
permissions granted by the host profile; `rules: []` denies everything. Each
rule selects one literal `s3://bucket` or `s3://bucket/key-prefix` path and
one or more permissions:

- `READ` — get or inspect objects.
- `LIST` — list a bucket within an allowed requested prefix.
- `WRITE` — put or copy objects and perform multipart upload operations.
- `DELETE` — delete objects or object versions.

S3 has no directories, so a trailing slash is significant:
`s3://bucket/team-a/` matches keys below that apparent directory, while
`s3://bucket/team-a` also matches a key such as `team-artifact`. Overlapping
rules combine permissions.

Unmatched requests fail closed. Copies require destination `WRITE` and source
`READ`. When rules are present, bucket administration, ACL, policy, tagging,
ListBuckets, bulk delete, and unknown operations are denied. AWS IAM remains the
final authority, so dedicated least-privilege host profiles are recommended.

## Client compatibility

The proxy streams content-length request and response bodies rather than
buffering whole objects. AWS CLI and endpoint-aware SDKs are supported. Clients
that hard-code AWS endpoints are not.

Generated configuration forces path-style addressing. Presigned URLs created
inside the sandbox are not portable, and chunked request bodies are rejected.
Non-AWS endpoints are not currently supported.
